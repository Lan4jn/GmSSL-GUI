# 离线更新说明（Linux amd64 / 达梦 DM8）

## 1. 独立使用范围与介质前提

本文从**新版本离线介质已经到达现场**开始，全部操作只访问本机和内网 DM8，无需阅读另一份说明或访问外部地址。适用于保留原数据库、账号、Vault 与主密钥的异目录更新。以下目录与介质位置均为示例占位，按现场实际替换。发布包版本为 0.1.5；包内顶层目录仍为 `gmssl-gui-linux-amd64/`，Java JAR 的 SNAPSHOT 名称与 DM schema 基线版本维持原值。

必须具备：

- 本次最终配套 `gmssl-gui-linux-0.1.5.tar.gz`。
- **成品镜像更新方式**还需要交付方提供 `gmssl-gui-images-linux-amd64.tar`；若所选方式缺少该 tar，停止更新。当前仓库尚未生成该镜像 tar。
- **本地 JRE 挂载更新方式**不需要该 GmSSL 应用镜像 tar，但依赖现场已有 Java 21/OpenSSL JRE 镜像和 Nginx 镜像，缺少时停止，等待匹配的离线镜像介质。
- Linux x86_64、Docker Engine 24+、Compose V2、Bash、tar、OpenSSL 与 Docker 管理权限。缺少 Docker/Compose 时，介质须提供匹配服务器发行版/版本/架构的离线安装包、全部依赖和安装指引，由系统管理员按配套流程安装，不臆造跨发行版命令。
- 原部署目录、原 `.env`、原凭据、实际 Vault 卷名称、内网 DM8 DBA 管理工具、维护窗口及可恢复的一致备份。

本说明对应最终配套版本；新版非空密码策略仍须由该版本平台镜像交付，不表示现场已更新。既有账号继续用原密码，修改 `.env` 的 bootstrap 密码不重置数据库已有用户。全程不运行初始化、不重新生成主密钥、不删除旧配置。

## 2. 解压新目录并只做计划预检

```sh
umask 077
mkdir -p /opt/gmssl-gui-v2
tar -xzf /media/offline/gmssl-gui-linux-0.1.5.tar.gz -C /opt/gmssl-gui-v2
cd /opt/gmssl-gui-v2/gmssl-gui-linux-amd64
bash ./upgrade.sh --from /opt/gmssl-gui-v1/gmssl-gui-linux-amd64 --plan
```

tar 顶层自带 `gmssl-gui-linux-amd64/`。`--from` 指向旧包含 `.env` 与 `compose.yaml` 的实际根目录，不是其上级。禁止原目录覆盖或用符号链接替代。`--plan` 只检查本地配置，不连接 DM8、不证明迁移完成。

管理员本地确认新旧 Compose 项目名一致，默认 `gmssl-gui-release`，实际 Vault 卷一致，默认 `gmssl-gui-release_vault-data`。DM8 地址必须从容器内部可达，外部库不要写容器自身的 localhost。保留原主密钥、engine token 和业务 schema；不要完整打印或上传 `.env`。

## 3. 在 load 同 tag 新镜像前保存旧镜像

必须先从**当前旧容器**确定实际 image ID，再保留独有回退 tag 并导出。新旧 tag 相同也执行。下列备份目录与标签若已存在，应改用新的名称，不覆盖旧备份。

```sh
umask 077
mkdir -p /opt/gmssl-backup-before-v2
cd /opt/gmssl-gui-v1/gmssl-gui-linux-amd64
ENGINE_CONTAINER=$(docker compose ps -q engine)
PLATFORM_CONTAINER=$(docker compose ps -q platform)
WEB_CONTAINER=$(docker compose ps -q web)
test -n "$ENGINE_CONTAINER" && test -n "$PLATFORM_CONTAINER" && test -n "$WEB_CONTAINER"
ENGINE_OLD=$(docker inspect --format "{{.Image}}" "$ENGINE_CONTAINER")
PLATFORM_OLD=$(docker inspect --format "{{.Image}}" "$PLATFORM_CONTAINER")
WEB_OLD=$(docker inspect --format "{{.Image}}" "$WEB_CONTAINER")
docker image tag "$ENGINE_OLD" gmssl-gui/engine:rollback-before-v2
docker image tag "$PLATFORM_OLD" gmssl-gui/platform:rollback-before-v2
docker image tag "$WEB_OLD" gmssl-gui/web:rollback-before-v2
docker image save -o /opt/gmssl-backup-before-v2/old-runtime-images.tar gmssl-gui/engine:rollback-before-v2 gmssl-gui/platform:rollback-before-v2 gmssl-gui/web:rollback-before-v2
```

旧容器不存在或无法识别旧镜像则停止，由管理员确认对应本地镜像。不要在 load 新包后才把同 tag 当成旧镜像备份。本节是保存运行镜像，不做文件校验。

## 4. 维护窗口与一致冷备

禁止新的用户写入，等待任务结束，停止应用，再由 DBA 备份原 DM8 schema 并记录恢复点。特别是状态型密钥任务运行时不能做不一致快照。保持停止直到备份与迁移结束。

```sh
cd /opt/gmssl-gui-v1/gmssl-gui-linux-amd64
bash ./stop.sh
cp -p .env /opt/gmssl-backup-before-v2/old.env
if [ -f credentials.txt ]; then cp -p credentials.txt /opt/gmssl-backup-before-v2/credentials.txt; fi
chmod 600 /opt/gmssl-backup-before-v2/old.env
cd /opt/gmssl-backup-before-v2
docker run --rm --pull=never --entrypoint /bin/tar --user 0:0 -v gmssl-gui-release_vault-data:/source:ro -v "$PWD":/backup gmssl-gui/engine:rollback-before-v2 czf /backup/vault-cold-backup.tar.gz -C /source .
```

使用刚保存的**本地旧 engine 镜像**，覆盖 entrypoint 为 `/bin/tar`、用 root 读取卷，并只读挂载源卷；不引入额外镜像。现场改过卷名时须先确认真实卷再替换，写错卷名可能生成空卷，命令成功不代表备对卷。

确认 DM8、Vault、含原 master key 的 `.env` 及凭据属于同一维护恢复点，备份权限受控且可恢复。不要删除卷，不用清理数据卷的命令，不运行 `init.sh`。

## 5. DBA 确认基线与所需增量

DBA 使用本地已有的内网 DM8 管理工具，确认原业务 schema 及当前版本：

- 没有 schema_version 时，审核并执行新包 `artifacts/migrations/00_schema_version_and_baseline.sql`。
- 已有 `0.1.0 / success=1` 可重入该脚本，仍先核实际 11 表、关键 BIT/VARBINARY 结构再幂等返回；旧 checksum 元数据保留，不作为文件匹配门禁。
- 失败状态或结构不符立即停止，不删除失败记录伪造成功；该脚本不是全约束比对。
- 若配套包确有后续增量，仅按迁移清单顺序执行尚未执行的脚本，不臆造不存在的迁移。

**已有业务库不得重跑 `artifacts/01_schema_dm8.sql` 初始化。** PL/SQL 块完整提交，不按分号盲拆。upgrade 脚本不会替 DBA 改库；`--backup-done` 同时确认一致备份完成与 DBA 迁移/兼容确认完成。

## 6. 应用更新与服务重建（两种方式二选一）

完成旧镜像保存、数据库备份、Vault 与配置冷备后，根据具备的运行镜像材料选择以下方式之一：

### 方式一：成品镜像方式（默认，推荐）
若交付方提供了新版本离线镜像包（`gmssl-gui-images-linux-amd64.tar`），先显式导入并检查，再执行受控升级：

```sh
cd /opt/gmssl-gui-v2/gmssl-gui-linux-amd64
bash ./load-images.sh /media/offline/gmssl-gui-images-linux-amd64.tar
docker image inspect gmssl-gui/engine:0.1.0-linux-amd64 >/dev/null
docker image inspect gmssl-gui/platform:0.1.0-linux-amd64 >/dev/null
docker image inspect gmssl-gui/web:0.1.0-linux-amd64 >/dev/null
bash ./upgrade.sh --from /opt/gmssl-gui-v1/gmssl-gui-linux-amd64 --apply --backup-done
docker compose --env-file .env -f compose.yaml up -d --pull never --no-build --force-recreate
bash ./status.sh
```

`--apply` 会校验并复制原 `.env` 与凭据至新目录、执行预检、停掉旧容器，最后以 `--pull never --no-build --force-recreate` 启动新容器，确保同 tag 下确实使用新镜像替换旧容器。

### 方式二：本地 JRE 挂载方式（无需 gmsslappimage.tar）
若现场只有新应用包（包含新版 JAR/二进制/前端产物），未生成新 GmSSL 业务镜像，可通过 `upgrade.sh` 显式传入 `--jre-image` 和 `--nginx-image` 执行平滑升级（自动调用新目录 `start-with-jre.sh` 挂载启动，绝不触发默认 `start.sh`）：

```sh
cd /opt/gmssl-gui-v2/gmssl-gui-linux-amd64
# 1. 只读预检（Plan 模式：前检新目录 JRE/Nginx 运行与挂载可行性，不改动任何旧文件与容器）
bash ./upgrade.sh --from /opt/gmssl-gui-v1/gmssl-gui-linux-amd64 --jre-image my-registry.local:5000/base/temurin:21-jre --nginx-image nginx:1.28-alpine --plan

# 2. 执行更新（Apply 模式：自动迁移配置、停止旧容器、并直接以指定 JRE 挂载启动新容器）
bash ./upgrade.sh --from /opt/gmssl-gui-v1/gmssl-gui-linux-amd64 --jre-image my-registry.local:5000/base/temurin:21-jre --nginx-image nginx:1.28-alpine --apply --backup-done
bash ./status.sh
```

**更新挂载约束**：新旧目录必须使用相同的 Compose 项目名（`gmssl-gui-release`）和数据卷（`gmssl-gui-release_vault-data`），确保业务材料与旧 Vault 无缝衔接；JRE 镜像需满足 Java 21 与 OpenSSL 运行要求。

任一步退出非零就停止后续命令并本地处理，不因打印成功就省略业务验证。新旧目录使用同一 Compose 项目和持久卷，不能另建空卷代替。

## 7. 更新后验收与密码材料说明

1. **登录与会话验证**：访问原内网入口，用**原账号密码**登录。登录请求及已登录 `/api/v1/auth/me` 应 200，未登录时 401 正常。直接内网 HTTP 设置 Secure Cookie=false；真正 HTTPS 入口为 true。
2. **简单模式 SM4 CBC 加密输出与解密约束**：
   - 简单模式下执行 SM4 CBC 加密输出为纯密文，**不自动在密文头部封装或拼接 IV**；
   - 随机生成的 16 字节 IV 会在页面上直观展示，用户**必须妥善复制并记录该 IV**；
   - 后续解密时必须显式提供该原始 IV（16 字节 Hex/字符串），**缺少原始 IV 无法恢复明文**，系统不假称可通过密文逆向还原。
3. **简单模式入口与证书制作向导**：
   - 简单模式导航精简为 4 项常用导航（工作台、密钥库、任务历史、项目与成员），首页工作台聚焦核心双卡（「制作证书」与「我的材料库」）；对称加解密等非证书工具彻底收敛隐藏，高级模式保持全量工具完整可用；
   - 证书向导包含 4 类核心卡片（单证自签名、根 CA、CSR 申请、已有 CA 快速签发），排除专业中间 CA 与双证书；快速签发在无可用 CA 时支持直接点击「创建根 CA」流转，不自动建根；
   - 证书与 CSR 文件生成后在结果页直观提供直接下载按钮，私钥与口令安全留存在密钥库中并独立二次确认；
   - 查看原项目、历史证书与密钥材料、能力目录和任务历史；不批量生成或用状态型签名“试运行”。
4. **密钥材料库与证书分类筛选**：
   - 密钥材料库在简单与高级两模式下均默认以证书树（按 CA 分组）展示，支持按项目切换或查看全部材料；
   - 证书树顶部提供签发 CA 过滤器（展示主体 CN、名称、序列号尾号及过期标记），支持按主体、文件名、序列号和签发者检索；
   - 根 CA、中间 CA、CA 签发终端证书、自签终端证书、CSR/缺失上级/待解析或不支持材料属于材料分类；历史过期 CA 可查看，但已过期 CA 标记为不可签发；
   - **材料分类、CA 归属关系与完整信任链是不同概念**；拓扑展示不单独证明完整信任链已经验证；本版本吊销状态为 `UNCHECKED`，不执行 OCSP/CRL 查询，不能据此宣称证书未被吊销。
5. **CSR 与证书双向关联与追溯边界**：
   - 在证书树中，由 CSR 生成或与其公钥匹配的证书节点下提供关联 CSR 下载入口与来源标识；CSR 列表中提供反向定位/跳转至匹配证书的快捷通道，支持一对多与多对多真实公钥验签关联；
   - **关联匹配不等于签发血缘，未匹配不等于未签发**：CSR 仅作为公钥申请凭证，不是证书签发的唯一来源；直接生成自签名证书或 CA 直签证书均无对应 CSR，未匹配仅代表当前项目中未找到对应公钥的 CSR 文件，不构成未签发或证书无效的结论。
6. **功能自检与运维**：
   - 可选 `bash ./scripts/verify-native.sh` 做原生密码能力功能测试；
   - 502 时本地查 `docker compose ps` 和 `docker compose logs --tail 100 platform engine web`；外发信息先脱敏，不提供 `.env`、Cookie、私钥及原 SQL 参数。

```sh
cd /opt/gmssl-gui-v2/gmssl-gui-linux-amd64
bash ./status.sh
```

确需维护时再执行 `bash ./stop.sh`，正常上线后保持运行。观察期内保留旧包、旧镜像、一致备份及更新记录。

## 8. 回退边界

脚本不自动回滚外部 DM8。出现问题先停止写入并保留现场，由 DBA 判断旧应用是否兼容当前 schema；普通应用回退也不能跳过数据库兼容性判断，不能仅切回旧目录。

确认兼容时，可在受控回退配置副本中明确指定三个已保存的 `rollback-before-v2` 本地镜像，保持原主密钥/同一 Vault，再以 `--pull never --no-build --force-recreate` 重建。不要重新初始化或重置账号。若需恢复数据，DB/Vault 应属于同一恢复点并评估期间新增数据。

**状态型密钥特别约束**：更新后如发生过签名或状态推进，恢复旧 DB/Vault 快照可能重复使用一次性状态。此时不要盲目倒退或复用旧密钥，须按负责人确认的状态型密钥恢复/隔离方案处理，不能套用普通回退流程。
